VoidForge یک برنامه بومی مبتنی بر Rust برای کار با **بسته‌های واقعی Void Linux** در محیط ترمینال است. این برنامه درخت مخزن محلی `void-packages` را باز می‌کند، فایل‌های Template را مستقیماً از روی دیسک می‌خواند، مراحل رسمی `xbps-src` را اجرا می‌کند، گزارش واقعی فرایند ساخت (Build Log) را به‌صورت زنده نمایش می‌دهد و به شما کمک می‌کند خطاها را به اطلاعات قابل‌استناد و مفید تبدیل کنید.

VoidForge یک کارگاه واقعی است، نه یک شبیه‌ساز. خبری از سرور Dashboard، مرورگر داخلی یا خروجی ساختگی نیست. وقتی VoidForge اعلام می‌کند که یک Build با موفقیت انجام شده، یعنی فرایند واقعی `xbps-src` با کد خروجی 0 به پایان رسیده است. وقتی هم می‌گوید یک Template مشکلی دارد، این نتیجه مستقیماً از فایل در حال ویرایش شما به دست آمده است.

```text
┌─ Dashboard ─────────────────────┬─ Build Center ────────────────────────────┐
│ HOST                            │ PHASE  build        PACKAGE  hello       │
│   Void Linux · x86_64 · glibc   │                                          │
│ TOOLS                           │ > xbps-src build hello                   │
│   xbps-src ✓   git ✓            │   => Building hello-1.0_1...            │
│   xbps-rindex ✓  curl ✓         │   => CC gcc ...                          │
│ RESOURCES                       │   => OK: hello-1.0_1 built               │
│   CPU 12%   RAM 1.4/8.0 GiB     │                                          │
│ ACTIVITY                        │STATUS  success (exit 0) · 47s            │
│   #12 build hello  success      │                                          │
└─────────────────────────────────┴──────────────────────────────────────────┘
: help   / filter   ? keys   q quit   Tab screens
```

> [!IMPORTANT]
> VoidForge را با حساب کاربری عادی خود اجرا کنید. **هرگز آن را با `sudo` اجرا نکنید.** فرایندهای Build در `xbps-src` باید بدون دسترسی Root اجرا شوند؛ اجرای برنامه با دسترسی Root باعث ایجاد فایل‌های متعلق به Root در Workspace و ذخیره تنظیمات در مسیر `/root` خواهد شد.

## چرا VoidForge؟

مدیریت بسته‌ها در Void Linux معمولاً مستلزم جابه‌جایی مداوم میان یک فایل Template در ویرایشگر، ترمینالی برای اجرای `xbps-src`، ترمینال دیگری برای دستورات `git` و یک فایل گزارش جداگانه برای بررسی خطاهاست.

VoidForge تمام این مراحل را در یک محیط کاری یکپارچه و مبتنی بر صفحه‌کلید گرد هم می‌آورد؛ بدون اینکه کنترل فایل‌ها و دستورات واقعی را از شما بگیرد.

قابلیت‌هایی که VoidForge در آن‌ها عملکرد خوبی دارد:

- **خواندن Templateهای واقعی:** فیلدهای چندخطی `depends`، توابع مربوط به Subpackageها، متغیرهای Shell و Checksumهای فایل‌های آرشیوشده، مطابق با ساختار واقعی Templateهای Void پردازش می‌شوند.
- **استفاده از ابزارهای رسمی:** عملیات Build با اجرای مستقیم `xbps-src <phase> <package>` و تعداد Jobهای تنظیم‌شده انجام می‌شود. هیچ بازپیاده‌سازی مستقلی از سیستم Build وجود ندارد.
- **ثبت و نگهداری شواهد:** هر عملیات Build یک فایل Log با زمان ثبت مشخص ایجاد می‌کند. ابزار تشخیص خطا، خطوط واقعی Log را برجسته می‌کند، نه حدس‌هایی که ارتباطی با خروجی واقعی ندارند.
- **احترام به ساختار مخزن شما:** دستورات Git با استفاده از آرایه آرگومان‌ها و جداکننده `--` اجرا می‌شوند. نام و مسیر Patchها اعتبارسنجی می‌شوند و عملیات Workspace بدون اجازه فایل‌های شما را حذف نمی‌کنند.
- **اجرای سریع:** صفحه اولیه هزاران Template را اسکن نمی‌کند. اطلاعات بسته‌ها فقط زمانی بارگذاری می‌شوند که واقعاً وارد صفحه مربوط به بسته‌ها شوید.
- **عملکرد بدون ایجاد مزاحمت:** تنظیمات، Indexها و تاریخچه در مسیرهای استاندارد XDG ذخیره می‌شوند. مخزن `void-packages` شما همچنان مرجع اصلی اطلاعات باقی می‌ماند.

## پیش‌نیازها

سیستم‌عامل هدف و پشتیبانی‌شده: **Void Linux با معماری x86_64 و کتابخانه glibc**.

سایر توزیع‌های لینوکس پشتیبانی نمی‌شوند؛ اجرای CI روی لینوکس عمومی صرفاً منطق داخلی برنامه را آزمایش می‌کند.

پیش‌نیازها:

- Rust و Cargo نسخه **1.89 یا جدیدتر** (در صورت Build از سورس)
- یک نسخه محلی از مخزن `void-packages` به همراه فایل اجرایی `./xbps-src`
- ابزارهای متداول Build در Void:
  `xbps-src`، `xbps`، `xbps-query`، `xbps-rindex`، `git`، `patch`، `curl`، `tar`، `bash` و `ninja`

نصب پیش‌نیازها در Void Linux:

```sh
sudo xbps-install -S rust git curl tar bash patch ninja xbps xbps-src
```

اگر از قبل یک Workspace از مخزن `void-packages` دارید، مسیر مطلق آن را یادداشت کنید؛ در بخش بعدی آن را به برنامه معرفی خواهید کرد.

در غیر این صورت، ابتدا مخزن را Clone کنید:

```sh
git clone https://github.com/void-linux/void-packages.git ~/void-packages
```

## نصب و اجرا

در حال حاضر کانال انتشار نسخه باینری وجود ندارد؛ بنابراین نصب برنامه از طریق دریافت و ساخت کد منبع انجام می‌شود:

```sh
git clone https://github.com/anomalogist/voidforge.git
cd voidforge
cargo build --release
./target/release/voidforge
```

**نصب اختیاری در سطح سیستم:**

```sh
sudo install -Dm755 target/release/voidforge /usr/local/bin/voidforge
voidforge
```

برای توسعه برنامه از `cargo run` استفاده کنید.

برای خروج می‌توانید از کلید `q`، کلید `Esc` در پنجره‌های محاوره‌ای یا ترکیب `Ctrl+C` استفاده کنید. اگر هنگام خروج یک Build فعال باشد، عملیات آن لغو شده و رکورد مربوط به آن در پایگاه داده با وضعیت `cancelled` علامت‌گذاری می‌شود.

## اولین تجربه کار با برنامه

این راهنما فرض می‌کند که مخزن `~/void-packages` از قبل روی سیستم شما وجود دارد و VoidForge را بدون تنظیمات قبلی اجرا کرده‌اید.

### ۱. ثبت Workspace

کلید `2` را فشار دهید تا وارد بخش **Workspaces** شوید. سپس دستور زیر را وارد کنید:

```text
:workspace add ~/void-packages
```

هم مسیرهای دارای `~` و هم مسیرهای مطلق پذیرفته می‌شوند.

VoidForge مسیر را گسترش می‌دهد، دسترسی به مسیرهای خارج از محدوده مجاز را رد می‌کند و مسیر مطلق را در پایگاه داده خود ذخیره می‌کند. Workspace بلافاصله در فهرست نمایش داده خواهد شد.

اگر ترجیح می‌دهید VoidForge مخزن را به‌جای شما Clone کند، از دستور زیر استفاده کنید:

```text
:workspace clone https://github.com/void-linux/void-packages.git void-packages
```

برای جابه‌جایی میان چند مخزن مختلف:

```text
:workspace use <name>
```

حذف یک Workspace با دستور زیر:

```text
:workspace remove <name>
```

توجه داشته باشید که این دستور فقط رکورد مربوط به Workspace را از پایگاه داده حذف می‌کند و هیچ تغییری در مخزن موجود روی دیسک ایجاد نخواهد کرد.

### ۲. بررسی ابزارهای موردنیاز

در صفحه Dashboard (`1`) باقی بمانید و بخش‌های **HOST** و **TOOLS** را بررسی کنید.

ابزارهای نصب‌نشده به‌صورت واضح نمایش داده می‌شوند و چیزی از شما پنهان نخواهد ماند.

اگر ابزاری وجود ندارد، آن را با `xbps-install` نصب کنید و سپس برای به‌روزرسانی وضعیت کلید `r` را فشار دهید.

برای بررسی دقیق‌تر می‌توانید دستور زیر را اجرا کنید:

```text
:workspace validate
```

با فشردن کلید `8` وارد بخش **Diagnostics** می‌شوید.

هر مورد شناسایی‌شده شامل عنوان، توضیح کوتاه و در صورت لزوم، مسیر دقیق فایل و شماره خط مربوطه خواهد بود.

### ۳. پیدا کردن یک Template

کلید `3` را فشار دهید تا وارد بخش **Packages** شوید.

در اولین ورود، اطلاعات دایرکتوری `srcpkgs` مستقیماً از دیسک بارگذاری می‌شوند.

برای فیلترکردن بسته‌ها بر اساس نام یا توضیحات، عبارت زیر را وارد کنید:

```text
/hello
```

با کلیدهای `j` و `k` میان نتایج حرکت کنید و برای بازکردن صفحه **Template** کلید `Enter` را فشار دهید.

صفحه Template متغیرهای پردازش‌شده، توابع Subpackage و نتایج اعتبارسنجی ایستا را نمایش می‌دهد.

- برای اجرای مجدد اعتبارسنجی در هر زمان، کلید `v` را فشار دهید.
- برای بازکردن فایل در ویرایشگر، کلید `e` را فشار دهید.

در VoidForge، ویرایشگر پیش‌فرض از متغیر محیطی `$EDITOR` گرفته می‌شود. برای تغییر آن می‌توانید از دستور زیر استفاده کنید:

```text
:editor "..."
```

پس از ویرایش موفق فایل، Template به‌صورت خودکار مجدداً بارگذاری می‌شود.

### ۴. اجرای اولین Build

با فشردن کلید `7` وارد بخش **Build Center** شوید.

با کلیدهای `j` و `k` یکی از مراحل Build را انتخاب کنید. فهرست مراحل از `bootstrap` شروع شده و تا `pkg` و `clean` ادامه پیدا می‌کند.

برای بسته‌ای که از قبل وجود دارد، معمولاً مرحله `pkg` انتخاب مناسبی است.

برای شروع عملیات کلید `b` یا `Enter` را فشار دهید.

- گزارش Build به‌صورت زنده نمایش داده می‌شود.
- کلید `x` درخواست لغو عملیات را ارسال می‌کند.
- نوار وضعیت، کد خروجی واقعی و مدت‌زمان اجرا را نمایش می‌دهد.

در نمای Log فقط زمانی کلید `r` را فشار دهید که به اطلاعات تازه Workspace نیاز دارید؛ جابه‌جایی میان صفحات به‌تنهایی باعث اسکن مجدد مخزن نمی‌شود.

### ۵. درک و بررسی خطاهای Build

وقتی یک Build با شکست مواجه می‌شود، VoidForge گزارش ذخیره‌شده را تحلیل می‌کند و در صورت موفقیت‌آمیزبودن تحلیل، بخش **Diagnostics** را باز می‌کند.

هر زمان که بخواهید می‌توانید این تحلیل را مجدداً اجرا کنید:

```text
:diagnose last
:diagnose 12
:build logs 0
```

یافته‌های تشخیصی به خطوط مشخصی از Log متصل هستند و به‌عنوان راهنمای مبتنی بر استنباط نمایش داده می‌شوند، نه علت قطعی خطا.

برای رسیدن به نتیجه دقیق، این اطلاعات را در کنار متن کامل Log و دانش خود درباره بسته بررسی کنید.

### ۶. آماده‌سازی و انتشار نتیجه

برای مشاهده بسته‌های ساخته‌شده از دستور زیر استفاده کنید:

```text
:release list
```

اگر یک مخزن باینری محلی را مدیریت می‌کنید، می‌توانید آن را Index کنید:

```text
:release index
```

این دستور فایل‌های آرشیو `.xbps` را فهرست کرده و `xbps-rindex -a -f` را روی آن‌ها اجرا می‌کند.

در نتیجه، بسته‌هایی که با همان نسخه قبلی دوباره ساخته شده‌اند، به‌روزرسانی می‌شوند و به‌اشتباه در وضعیت قدیمی باقی نمی‌مانند.

برای بررسی Metadata یک بسته:

```text
:release info <name>
```

در نهایت، کار خود را از بخش **Git & Repos** بررسی و Commit کنید:

```text
:git status
:git diff
:git stage srcpkgs/hello/template
:git commit "hello: update to 1.1"
:git push origin master
```

عملیات مربوط به Remoteها پیش از اجرا به تأیید شما نیاز دارند.

Branchها و Remoteها پیش از ارسال به Git اعتبارسنجی می‌شوند و مقادیر مشابه گزینه‌های اجرایی، مانند `--upload-pack=...`، رد خواهند شد.

## آشنایی با بخش‌های مختلف برنامه

برای رفتن مستقیم به هر صفحه، کلیدهای `1` تا `0` را فشار دهید. همچنین می‌توانید با `Tab` و `Shift+Tab` میان صفحات جابه‌جا شوید.

| کلید | بخش | قابلیت‌ها |
| --- | --- | --- |
| `1` | **Dashboard** | نمایش اطلاعات میزبان، تشخیص glibc/musl، وضعیت ابزارها، CPU، حافظه، Swap و تاریخچه اخیر |
| `2` | **Workspaces** | ثبت، Clone، اعتبارسنجی، به‌روزرسانی، جابه‌جایی و حذف Workspaceهای `void-packages` |
| `3` | **Packages** | مرور `srcpkgs`، فیلترکردن، ایجاد، تکثیر، تغییر نام و بازکردن Templateها |
| `4` | **Template** | نمایش متغیرها، توابع، بررسی‌های ایستا و یکپارچگی با ویرایشگر خارجی |
| `5` | **Dependencies** | بررسی `depends`، `makedepends`، `hostmakedepends` و `checkdepends` همراه با شواهد مخزن و میزبان |
| `6` | **Patches** | فهرست‌کردن، پیش‌نمایش، ایجاد، تولید از Git Diff، اعمال و بازگردانی Patchها همراه با نسخه پشتیبان |
| `7` | **Build Center** | اجرای مراحل رسمی `xbps-src`، نمایش زنده Log، لغو عملیات، تاریخچه Build و بسته‌های خروجی |
| `8` | **Diagnostics** | نمایش یافته‌های مبتنی بر Log برای Buildها، Templateها، Workspaceها و چرخه‌های وابستگی |
| `9` | **Git & Repos** | مدیریت Status، Branchها، Remoteها، Diffها، Stage/Unstage، Commit، Fetch، Pull، Push و Tagها |
| `0` | **Settings** | تنظیم پوسته روشن یا تاریک، تعداد Jobهای موازی (1 تا 64)، فرمان ویرایشگر و ترجیحات ایمنی |

چند نکته مهم:

- نوار وضعیت همیشه پیام فعلی و یک راهنمای کوتاه را نمایش می‌دهد.
- کلید `?` راهنمای کامل کلیدها و دستورات داخل برنامه را باز و بسته می‌کند. کلید `Esc` برای بستن راهنما، پنجره‌های محاوره‌ای یا پیام فعلی استفاده می‌شود.
- فیلترها هم نام بسته‌ها و هم توضیحات آن‌ها را بررسی می‌کنند.
- با انتخاب یک بسته جدید، اطلاعات تشخیصی قدیمی پاک می‌شوند تا یافته‌ها همیشه به Template فعلی مربوط باشند.
- دایرکتوری‌های Build که تحت کنترل Git نیستند، مانند `masterdir`، `hostdir` و `.git`، هنگام گسترش وضعیت Git نادیده گرفته می‌شوند تا Workspaceهای بزرگ همچنان عملکرد روانی داشته باشند.

## گردش‌کارهای روزمره

### ایجاد و تکثیر یک بسته

```text
:pkg new mypackage
:pkg duplicate mypackage mypackage-git
:pkg rename mypackage old-mypackage
```

دستور `pkg new` یک Template حداقلی ایجاد می‌کند که تمام فیلدهای ضروری را دارد، اما مقدار آن‌ها خالی است.

پیش از اجرای Build باید فیلدهای زیر را تکمیل کنید:

`version`، `short_desc`، `maintainer`، `license`، `homepage`، `distfiles` و `checksum`.

دستور `pkg rename` دایرکتوری بسته را روی دیسک جابه‌جا کرده و مقدار `pkgname` در سطح اصلی Template را بازنویسی می‌کند؛ حتی اگر Subpackageها در ابتدا به‌صورت Symlink ایجاد شده باشند.

### اطمینان از صحت فایل‌های منبع

```text
:source verify
:source download 0
:source extract hello-1.0.tar.gz
:source github https://github.com/owner/project
```

- `verify`: Checksumهای تعریف‌شده را با فایل‌های موجود در Source Cache مقایسه می‌کند.
- `download`: فایل Distfile را با محدودیت زمانی دریافت کرده و نام‌های ناامن و مقصدهای Symlink را رد می‌کند.
- `extract`: محتویات آرشیو را در یک دایرکتوری محدود و کنترل‌شده استخراج می‌کند.
- `source github`: از GitHub API برای دریافت آخرین Release Tag استفاده می‌کند.

### کار با Patchها

```text
:patch new fix-build.patch
:patch from-git fix-build.patch src/configure.ac
:patch apply fix-build.patch
:patch revert fix-build.patch
:patch remove fix-build.patch
```

یک Patch جدید در ابتدا خالی ایجاد می‌شود؛ سپس باید آن را با ویرایشگر دلخواه خود ویرایش کنید.

دستور `from-git` یک Unified Diff نسبت به `HEAD` ایجاد می‌کند که تغییرات Staged را نیز در بر می‌گیرد.

دستورات `apply` و `revert` پیش از اعمال تغییرات، Patch را اعتبارسنجی می‌کنند و از تمام فایل‌های تحت‌تأثیر نسخه پشتیبان با نامی منحصربه‌فرد می‌سازند.

اگر دستور `patch` در میانه عملیات شکست بخورد، فایل‌های موردنظر از نسخه‌های پشتیبان بازیابی می‌شوند.

نام Patchها نمی‌تواند شامل دایرکتوری یا عبارت `..` باشد. همچنین مسیرهای موجود در Diff پیش از دست‌زدن به هر فایلی بررسی می‌شوند.

### تحلیل چرخه‌های وابستگی

```text
:dependencies     (or view 5)
:deps cycles      -> opens Diagnostics
```

تحلیل چرخه‌های وابستگی، هر چهار فیلد مربوط به Dependency را پردازش می‌کند، Subpackageهای دارای Symlink را برای جلوگیری از ایجاد گره‌های غیرواقعی کنار می‌گذارد، چرخش‌های معادل چرخه‌ها را یکسان‌سازی می‌کند و هر چرخه متمایز را فقط یک بار گزارش می‌دهد.

## محل ذخیره‌سازی اطلاعات

VoidForge عمداً مقدار بسیار کمی از اطلاعات را به‌صورت مستقل ذخیره می‌کند.

| مسیر | محتویات |
| --- | --- |
| `~/.local/share/voidforge/voidforge.sqlite3` | تنظیمات، فهرست Workspaceها، تاریخچه Build و Git و اعلان‌ها |
| `~/.local/share/voidforge/logs/` | فایل‌های Log زمان‌دار `xbps-src` که توسط دستور `:diagnose` استفاده می‌شوند |
| `$XDG_DATA_HOME/voidforge/...` | همان ساختار، در صورت تنظیم متغیر `XDG_DATA_HOME` |
| مخزن `void-packages` شما | Templateها، Patchها، فایل‌های منبع، خروجی‌های Build و مخزن Git |

Migrationهای پایگاه داده در فایل اجرایی برنامه قرار گرفته‌اند و هنگام راه‌اندازی، مستقیماً روی پایگاه داده موجود اعمال می‌شوند.

حذف یک Workspace هیچ‌گاه فایل‌های مخزن را حذف نمی‌کند و هیچ‌یک از دستورات VoidForge دایرکتوری `void-packages` شما را پاک نخواهند کرد.

## ملاحظات امنیتی و محدودیت‌ها

- فقط Void Linux با معماری x86_64 و کتابخانه glibc پشتیبانی شده و مورد آزمایش قرار گرفته است.
- اعتبارسنجی ایستای Template می‌تواند اشتباهات رایج را شناسایی کند، اما نمی‌تواند موفقیت قطعی `xbps-src` را تضمین کند.
- Buildها با استفاده از ابزارهای واقعی نصب‌شده روی سیستم شما انجام می‌شوند. وابستگی‌های نصب‌نشده یا Masterdirهای خراب گزارش می‌شوند و پنهان نخواهند ماند.
- عملیات شبکه دارای محدودیت زمانی هستند و هیچ‌گاه برای دریافت اطلاعات احراز هویت، به‌صورت تعاملی درخواست ورود اطلاعات نمی‌کنند.
- Patchها پیش از دسترسی به فایل‌ها بررسی می‌شوند. در صورت شکست عملیات، تغییرات با استفاده از نسخه‌های پشتیبان منحصربه‌فرد بازگردانی می‌شوند. فایل‌های Reject با پسوند `.rej` برای بررسی باقی می‌مانند.
- VoidForge رشته‌های Shell ساخته‌شده از ورودی کاربر را اجرا نمی‌کند. دستورات با آرایه آرگومان‌ها اجرا می‌شوند و مسیرهای استخراج‌شده از Templateها یا Diffها از نظر محدودیت مسیر بررسی می‌شوند.
- پایگاه داده‌های بسیار قدیمی با استفاده از Migrationهای تعبیه‌شده، در همان محل ارتقا پیدا می‌کنند. اگر قصد آزمایش و بازگشت به وضعیت قبلی را دارید، یک نسخه پشتیبان نگه دارید.

## عیب‌یابی

**هنگام اجرا پیام `not a terminal` نمایش داده می‌شود.**

VoidForge به یک TTY واقعی نیاز دارد. برنامه را در یک شبیه‌ساز ترمینال اجرا کنید، نه از طریق Pipe کردن خروجی یا اجرای آن در یک اسکریپت CI.

**پس از Crash، ظاهر ترمینال به‌هم می‌ریزد.**

VoidForge از یک Panic Hook استفاده می‌کند که حالت Raw و صفحه جایگزین ترمینال را هنگام خروج بازیابی می‌کند؛ بنابراین وقوع این مشکل باید نادر باشد.

اگر همچنان با این مشکل مواجه شدید، دستور زیر را در ترمینال اجرا کنید:

```sh
reset
```

یا از دستورات زیر استفاده کنید:

```sh
stty sane
clear
```

**هیچ بسته‌ای نمایش داده نمی‌شود.**

Workspace فعال را در صفحه `2` بررسی کنید، مطمئن شوید دایرکتوری `srcpkgs` وجود دارد و سپس دستورات زیر را اجرا کنید:

```text
:workspace validate
r
```

Templateهایی که خواندن آن‌ها با مشکل مواجه شود، به‌صورت جداگانه نادیده گرفته می‌شوند تا کل مخزن از دسترس خارج نشود.

**برخی ابزارها به‌عنوان نصب‌نشده نمایش داده می‌شوند.**

ابزارهای موردنیاز را نصب کنید:

```sh
sudo xbps-install -S ...
```

سپس کلید `r` را فشار دهید.

بررسی ابزارها به اجرای موفق یک دستور و دریافت خروجی‌ای با ساختار مشابه نسخه نرم‌افزار نیاز دارد.

**Build شکست خورده اما متن Diagnostics نمایش داده نمی‌شود.**

گزارش خام را با دستور زیر باز کنید:

```text
:build logs <index>
```

تحلیل خطا فقط زمانی یافته‌های قبلی را جایگزین می‌کند که بتواند فایل Log را بخواند و تحلیل کند. شکست در فرایند تحلیل، هیچ‌گاه شواهد قبلی را به‌صورت بی‌صدا بازنویسی نمی‌کند.

**دستور `:git pull` درخواست Checkout یک Branch را نمایش می‌دهد.**

احتمالاً مخزن در وضعیت Detached HEAD قرار دارد و Branch فعالی برای دریافت تغییرات ندارد.

ابتدا یک Branch را Checkout کنید:

```text
:git checkout <branch>
```

**هنگام اعمال Patch، پیام Rejection دریافت می‌کنید.**

فایل‌های `.rej` را در کنار فایل‌های منبع مربوطه بررسی کنید.

VoidForge نسخه اصلی فایل‌ها را با استفاده از نسخه‌های پشتیبان بازیابی کرده است. Patch را اصلاح کنید و دوباره آن را اعمال کنید.

**نام بسته‌ای که با حرف بزرگ شروع می‌شود رد می‌شود.**

چنین نام‌هایی نباید رد شوند؛ نام‌هایی مانند `R-cran-foo` و `AppStream` معتبر هستند.

اگر با این مشکل مواجه شدید، لطفاً آن را به‌عنوان یک Bug گزارش کنید.

## ساختار پروژه

```text
src/
├── app.rs              مدیریت State، پردازش دستورات، کلیدها و تأییدها
├── build.rs            مدیریت فرایند xbps-src و رویدادهای جریانی
├── db.rs               Indexهای SQLite، تنظیمات و تاریخچه Build/Git
├── deps.rs             پردازش وابستگی‌ها و شناسایی چرخه‌ها
├── diagnostics.rs      قوانین تشخیص خطا بر اساس شواهد واقعی Build Log
├── events.rs           کانال رویدادهای TUI
├── git.rs              Wrapper امن Git بدون تفسیر Shell
├── models.rs           مدل‌های مشترک دامنه
├── package.rs          پردازش Templateها و عملیات srcpkgs
├── patches.rs          اعتبارسنجی، اعمال، بازگردانی و تهیه نسخه پشتیبان Patchها
├── release.rs          فهرست binpkgها، Metadata و xbps-rindex
├── source.rs           فایل‌های distfile، Checksum، دانلود، استخراج و GitHub Tags
├── system.rs           تشخیص میزبان و ابزارها و نمونه‌برداری از شاخص‌های سیستم
├── template.rs         اعتبارسنجی ایستای Template
├── tui/
│   ├── mod.rs          چرخه عمر ترمینال و حلقه رویداد
│   ├── render.rs       رندر تمام صفحات با Ratatui
│   └── theme.rs        پالت‌های رنگی روشن و تاریک
├── utils/path.rs       گسترش مسیرها و بررسی محدوده Workspace
└── workspace.rs        ثبت و اعتبارسنجی Workspace
```

تغییرات مربوط به Schema پایگاه داده در دایرکتوری `migrations/` قرار دارند و هنگام کامپایل در فایل اجرایی برنامه تعبیه می‌شوند.

## توسعه و CI

مجموعه بررسی‌های کیفیت پروژه عمداً کوتاه نگه داشته شده است تا بتوان پیش از هر Commit آن را اجرا کرد:

```sh
cargo fmt --all -- --check
cargo check --all-targets
cargo test --all-targets
cargo clippy --all-targets -- -D warnings
cargo build --release
```

همین دستورات در فایل `.github/workflows/ci.yml` و با هر Push یا Pull Request اجرا می‌شوند.

آزمایش‌ها شامل Unit Testها و Integration Testهایی هستند که روی یک مخزن آزمایشی `void-packages` اجرا می‌شوند.

موارد تحت آزمایش عبارت‌اند از:

- اسکن و اعتبارسنجی Templateها
- بررسی وابستگی‌ها
- مدیریت Patchها
- Metadata مربوط به Git
- فهرست‌کردن نسخه‌های قابل انتشار
- اجرای `xbps-src` با استفاده از یک اسکریپت جایگزین (Stub Script)

مجموعه تست‌ها به دسترسی شبکه یا اجرای Build واقعی نیاز ندارد.

گزارش Bug و ارسال Pull Request از سوی مشارکت‌کنندگان استقبال می‌شود.

لطفاً هنگام گزارش مشکل، نسخه Void Linux، دستور دقیقی که اجرا کرده‌اید و بخش مرتبط از Log را نیز ارائه دهید.

عبارت «کار نکرد» اطلاعات کافی برای بررسی مشکل در اختیار توسعه‌دهندگان قرار نمی‌دهد؛ درحالی‌که معمولاً پنج خط خروجی واقعی برای شروع بررسی کافی است.
